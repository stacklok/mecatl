# ADR 0350 — Durable workspace-enrollment broker authority provenance

- Status: Proposed — remains proposed until the Plan / Interface PR receives human merge approval.
- Date: 2026-09-21
- Scope: session authority replacement, persistence, successor boundary, collision handling, and enrollment failure presentation for ToolHive workspace enrollment
- Supersedes: ADR 0335 Decision 6 only
- Superseded by: None

## Context

Workspace enrollment installs an authenticated, session-bound broker catalog beside the ordinary composed catalog. The existing completion path replaces the aggregate's complete durable tool capability set with enrolled catalog names. That drops unrelated core, delegation, memory, skill, global/client-MCP, MCP-resource, and latent-member capabilities, even though they remain part of the session's authority.

A final-catalog intersection is not sufficient: durable authority includes opaque MCP-resource and latent-member capabilities that are not registrations. Nor can the broker bundle be inferred after restart from `ExternalBinding`: bindings and attachments are process-local, while snapshots contain an undifferentiated authority set. The necessary durable distinction is therefore only the exact registration keys installed by a successful workspace-enrollment broker bundle—not origin metadata for every catalog entry.

The control checks session ownership, a configured broker, idle state (reopening completed sessions), and no live run; the aggregate also rejects conflicting controls. Permission denies/asks are separate from capability membership: `internal/adapter/permconfig/permconfig.go` (`rulesFromConfig`) and `engine/adapter/permpolicy/permpolicy.go` (`Evaluate`) keep them effective, while mode and profile filtering remain unchanged. `internal/adapter/server/service.go` (`setPerSessionLabels`) explicitly avoids adding broker/client capabilities to carried authority at creation, but does add the attachment's broker keys to fresh authority, so those keys need provenance from the moment of creation. The supported surfaces do not expose arbitrary per-key capability editing. Delegation narrows child authority and inherits the parent's owner, but does not copy `ExternalBinding` (`engine/agent/subagent.go`, `engine/agent/child_environment.go`). `internal/adapter/server/workspace_enrollment.go` (`workspaceEnrollmentTarget`) requires a binding: `internal/adapter/server/mcp_broker.go` (`openBrokerAttachment`) rejects an empty binding before broker lookup/attachment. This is not the mismatch error that permits rebind. `internal/adapter/server/service.go` (`managementSession`) also rejects child kinds/prefixes from clear/fork, so a child cannot acquire a successor binding there. The previously claimed supported child-enrollment journey is blocked, despite the absence of a root-kind filter in enrollment. This proposal authorizes no widening of narrowed child authority; arbitrary capability editing and custom-host placement of such sessions are outside scope. If another supported journey is established, implementation must stop for a narrow plan decision, not silently regrant authority.

MCP remote tools commonly use `mcp__<server>__<tool>` keys, so a broker/non-broker collision is rare. It remains unsafe: an exact durable key must not silently select a different source's implementation. This guard protects Mecatl's final cross-source registration boundary only; ToolHive continues to own its internal prefixes and conflict resolution.

## Decision

1. `Session` owns a private, bounded, exact workspace-enrollment broker-key ledger and a presence bit. `session.New` starts with absent provenance. Every server root-creation path sets authority and ledger together: a fresh session records present provenance holding exactly the broker registration keys it granted (present-empty when none), and every authority-carrying path (clear, fork, and `CreateSession` with a source session) copies the source ledger and presence bit. A path that forgets the ledger therefore fails closed (enrollment refused) instead of treating stale broker keys as non-broker authority. Present-empty records known empty provenance, not proof of completed enrollment; absent means unrepaired legacy provenance. The ledger contains only registration keys, not endpoints, connector metadata, OAuth state, credentials, tool schemas, bindings, or runtime handles.
2. The minimal engine API addition is `Session.WorkspaceEnrollmentBrokerKeys() ([]string, bool)` and `Session.RestoreWorkspaceEnrollmentBrokerKeys([]string, bool) error`. The accessor returns a copy and presence; the restore method validates copied provenance during idle snapshot restoration, root creation, or successor construction, before history/control restoration, and is write-once. `CompleteWorkspaceEnrollment(pending, exactTools)` retains its signature, but `exactTools` is documented as the completed broker registration-key bundle. Let `excluded prior broker keys = prior broker keys − prior authority`; completion atomically computes `(prior authority − prior broker keys) + (completed broker keys − excluded prior broker keys)` and replaces the ledger with `completed broker keys ∪ excluded prior broker keys`, so an exclusion survives a refresh that omits the key. A union exceeding the ledger bounds fails completion without mutation. Within the existing enrollable root/successor flow, this preserves all non-broker membership and absence, preserves exclusion of previously recorded broker keys, and admits genuinely new broker keys. It neither makes narrowed children enrollable nor authorizes overriding their carried restrictions. Configured denies/asks, mode/profile enforcement, and non-tool authority axes remain unchanged.
3. `sessnap.Snapshot` persists `workspace_enrollment_broker_keys []string \`json:"workspace_enrollment_broker_keys,omitempty"\`` and `workspace_enrollment_broker_keys_present bool \`json:"workspace_enrollment_broker_keys_present,omitempty"\``. Both fields absent means legacy absent provenance. `workspace_enrollment_broker_keys_present:true` with the keys field absent, `null`, or an empty array means present-empty; the same true field with a valid nonempty array means present-nonempty. Normal Go JSON slice decoding therefore accepts `null` as zero keys, while the explicit presence bit retains the security distinction. Raw JSON validation rejects nonempty keys without true presence, null/non-boolean presence, non-array or non-string key data, and malformed, duplicate, or over-bound keys before aggregate restore. `sessnap.Of` reads the ledger through the accessor; `Snapshot.Restore` applies it through the restore method. `eventsource.SessionMeta` carries the same exact keys and presence bit as external creation metadata and restores them by the same method before event folding; no enrollment event is created or consumed. Its false/absent value is the same legacy-absent ledger, which the server enrollment guard refuses; an event-log host must supply true plus exact keys to reconstruct an enrollment-capable session. In the server, `workspaceEnrollmentTarget` checks present, valid provenance immediately after `Store.Load` and owner authorization, before the existing completed-session `Reopen`/save, reset, attachment open/rebind, discovery, consent, or runtime mutation. Absent legacy data remains absent and is rejected at that guard. It is not inferred or repaired; a fresh session is the recovery path.
4. Snapshot restore preserves an enrollment ledger but never resurrects broker runtime. Ordinary rehydration continues to build without broker attachment/wrappers from persisted broker keys or binding. Only an explicit owner control can establish a fresh attachment and completed bundle. Clear and fork carry the source ledger and presence bit alongside carried authority, so a later refresh can subtract inherited broker keys. They create fresh broker attachments/bindings and do not copy the source's completed enrollment, pending operation, or runtime. Provenance is subtraction evidence, not connectivity. Engine construction, attachment commit, aggregate completion, or snapshot persistence failure leaves prior authority and ledger unchanged and publishes no partial replacement; destructive refresh may leave broker runtime unavailable.
5. Composition records the exact broker keys from the one final catalog registration pass. It must use an error-returning dynamic registration path—not `MustRegister`—and return a safe duplicate-key classification plus the registered-key metadata through the existing root-internal factory/result handoff. Registration metadata is captured in that pass, with no second `Tool.Spec()` call. Before candidate publication, it rejects a current non-broker registration matching either an incoming key or a prior ledger key that is still held in authority. The same prior-key refusal applies to every engine build for the session (rehydrate and successors, not only enrollment) and surfaces as a failed-precondition error naming only the safe key; excluded keys absent from authority never trigger it. Collision fails the complete bundle: no candidate wrapper, binding, authority, or provenance is published. The only allowed durable cleanup is clearing the pending enrollment, which an enrollment-time collision or ledger-bound overflow must do (and persist) so the session accepts prompts again; after destructive refresh, broker runtime may remain unavailable while prior durable authority and ledger remain unchanged.
6. The owner receives a terminal failure naming only the safe conflicting registration key and retry-after-configuration-correction guidance. Unauthorized callers stay on the existing concealed not-found-style path and receive neither that key nor state information. Neither path exposes OAuth URLs, endpoints, callback state, credentials, tokens, or connector configuration. Mecatui shows the terminal failure, does not send a prompt retained pending success, and retains the existing explicit retry path after settlement.
7. This supersedes only ADR 0335's “no refresh-specific persisted state” clause. Its whole-bundle, explicit-control, ToolHive-custody, destructive replacement, ordered-publication, and no-partial-catalog decisions remain unchanged.

## Consequences

Successful enrollment and refresh no longer clobber unrelated session authority, while a later refresh removes known old broker keys exactly. A previously recorded broker key removed from carried authority remains excluded even when the refreshed bundle registers it again; genuinely new broker keys can still be admitted. The ledger is narrow provenance, not a general catalog-source model or arbitrary authority editor. Existing supported restrictions remain intact: owner/idle/control eligibility, configured permission denies/asks, session mode/profile enforcement, non-tool authority axes, and exact non-broker membership and absence.

A restart retains the authority ledger but not a live broker capability. An explicit post-restart refresh can subtract the old recorded broker keys and install only a newly verified bundle. A clear or fork carries the subtraction ledger with authority while establishing its own fresh attachment, not inheriting a source's connection.

A rare deployment collision fails visibly for the owner rather than silently choosing precedence or omitting a tool. If the colliding non-broker tool appears after enrollment, the session cannot run at all until the operator corrects the configuration; this trades availability for the guarantee that a durable key never resolves to a different implementation.

An older binary re-saving a snapshot drops the ledger fields (for example during a rolling update over a shared store). The session then reads as legacy and refuses enrollment permanently; release notes must say so. The mechanism neither replaces ToolHive's own collision policy nor adds a cross-source framework.

The new accessors are Added/minor. Changing the existing exported `CompleteWorkspaceEnrollment` replacement semantics and refusing legacy enrollment requires separate behavioral compatibility review under `engine/COMPATIBILITY.md`; an unchanged signature does not imply additive compatibility (Changed is breaking under that policy). `task api:update`, the `engine/api/session.txt` baseline, and the separately classified `engine/CHANGELOG.md` entries are implementation deliverables, not plan-approval prerequisites. No protobuf, RPC, config, command, event, or model-facing surface changes.

## Rejected alternatives

- **Replace authority with final catalog names.** This deletes opaque/non-registered capabilities and can widen intentionally attenuated authority.
- **Union prior authority with enrolled names.** This retains stale broker keys that could later name an unrelated registration.
- **Persist origin metadata for every catalog entry.** Only workspace-enrollment broker keys need durable provenance.
- **Treat `/tools-connect` as authority administration.** The control is an existing owner-authorized broker enrollment path, not permission to override session restrictions.
- **Fail the whole refresh when a previously recorded broker key was excluded from carried authority.** The complete bundle can still register while authority disclosure preserves the exclusion; failure would unnecessarily block unrelated or genuinely new broker keys in the same refresh.
- **Discard successor provenance because its attachment is fresh.** Carried authority still contains old broker keys; dropping their ledger prevents exact subtraction at the successor's next refresh. Copy provenance, never completed enrollment or runtime.
- **Omit conflicting broker tools or choose a source precedence.** The broker bundle is atomic, and redirecting a durable key to another implementation changes authority.
- **Reimplement ToolHive conflict resolution.** Mecatl needs only the final cross-source registration safeguard.
- **Repair legacy snapshots heuristically.** Their authority cannot distinguish accidental loss from deliberate attenuation.
