# Idle-session MCP broker workspace refresh — acceptance plan

**Contract:** human-reviewed/v2
**Work classification:** Architectural — changes durable session authority, broker-binding recovery, and supported mecak8s deployment behavior.
**Decision record:** [ADR 0335](../adr/0335-idle-session-broker-workspace-refresh.md)
**Phase:** Session-scoped protected-tool refresh and restart recovery
**Status:** proposed, 2026-09-14. The directing human settled the product and implementation-contract decisions in this conversation; ready for Plan / Interface review.
**Delivery:** Split. The change alters session authority/persistence semantics, a public control's eligibility, restart behavior, and broker deployment documentation.
**Expected tasks:** deferred to orchestration.
**Issue:** [#1463](https://github.com/stacklok/mecatl/issues/1463)
**Plan PR:** absent until opened.
**Approved baseline:** absent until the Plan / Interface PR merges.

A caller who owns an idle broker-backed mecak8s session can run `/tools-connect` after any completed conversation turn. The existing `ConnectWorkspaceServices` gRPC/HTTP control starts, observes, retries, or cancels one ToolHive-owned whole-bundle operation. Starting refresh is an explicit destructive replacement: active broker wrappers become unavailable until a complete verified replacement succeeds. No connector selector, new command grammar, or new wire message is introduced.

A successful authenticated discovery installs the session's replacement broker-owned catalogue and engine for later turns through one serialized, fail-closed publication sequence. The sequence is not a transaction across broker memory, engine registration, and `SessionStore`: “connected” is reported only after complete discovery, engine construction, aggregate update, and snapshot persistence succeed, and every failed or interrupted boundary must leave no executable broker wrapper. When the broker process has restarted, the session must remain usable without broker tools until its owner explicitly refreshes; it must not infer executable tool authority from stale persisted names or initiate browser consent from an ordinary prompt. [ADR 0335](../adr/0335-idle-session-broker-workspace-refresh.md) records the durable decision; the current broker lifecycle is in [`internal/adapter/server/workspace_enrollment.go`](../../internal/adapter/server/workspace_enrollment.go) and [`internal/adapter/server/mcp_broker.go`](../../internal/adapter/server/mcp_broker.go).

## Human decisions

- [x] Model refresh notification — Decision: do not add a synthetic conversation message, prompt instruction, or model-visible refresh event; the next request's refreshed tool definitions are the sole model-facing indication.
- [x] Refresh scope and completion — Decision: `/tools-connect` refreshes the complete configured protected connector bundle; authenticated discovery must succeed for every configured connector before one replacement is admitted. No per-connector selection, partial success, additive merge, or confirmation step is added.
- [x] Active-catalogue failure behavior — Decision: `/tools-connect` is an explicit destructive replace-connection operation. Starting a refresh withdraws active broker wrappers and invalidates their completed-catalogue generation before beginning the replacement ToolHive operation. Persisted capability names alone are inert metadata and never authorize execution without the exact live binding and wrappers. A failed, denied, cancelled, or expired replacement leaves broker tools unavailable; only verified complete discovery installs a new broker catalogue, binding, and engine. No incumbent/candidate generation or rollback guarantee is required.
- [x] Broker refresh lifecycle — Decision: add one narrow root-internal broker operation that retires the completed catalogue/active generation and permits a new whole-bundle enrollment while preserving the logical ToolHive session. Do not use the durable `DeleteSession` teardown or the server's broad session-local cleanup. Grant reuse is not guaranteed: ToolHive alone decides whether its configured storage and lifecycle can reuse a valid held grant or require consent.
- [x] Control concurrency — Decision: begin/observe/cancel is allowed only from an owned idle session with no active run, pending permission/lazy authorization, or another workspace refresh. Retry is one run-entry-serialized cancel-and-begin operation, so no prompt can enter between those phases. While a refresh is pending, new prompts are rejected until it reaches a terminal state or is cancelled.
- [x] Restart recovery — Decision: after broker-process loss, keep the same session usable without active broker tools. Its owner explicitly invokes `/tools-connect` to create a fresh attachment and restore a verified complete catalogue; an ordinary prompt never triggers recovery or browser consent.
- [x] Upstream grant handling — Decision: mecatl makes no grant-reuse guarantee. The refresh preserves the logical ToolHive session rather than invoking durable session deletion; ToolHive may reuse a valid held grant only when its configured storage and lifecycle permit it, and otherwise requests consent. Mecatl never exposes, copies, selects, or persists upstream grant material.
- [x] Deployment topology — Decision: retain broker-enabled mecak8s as single-replica. This work introduces neither affinity/routing nor a distributed/remote broker runtime.
- [x] Stable-point lifecycle — Decision: `/tools-connect` invoked after a completed turn uses the existing completed-to-idle `Session.Reopen` transition before it begins refresh. Reopen preserves conversation history and uses the existing owner/lease/run-entry serialization; a terminal refresh leaves the session idle and reusable.
- [x] Static declared-tool behavior during destructive replacement — Decision: starting `/tools-connect` also withdraws ADR 0310's static declared protected-tool wrappers until replacement succeeds. A failed replacement leaves no broker tools usable; initial-session static/lazy authorization remains unchanged when no explicit replacement is underway.

## Interface contract

- **gRPC / protobuf:** No schema or RPC addition. Existing `HarnessService.ConnectWorkspaceServices`, `RetryWorkspaceEnrollment`, and `CancelWorkspaceEnrollment` retain their request/response messages, field numbers, and aggregate presentation-safe status vocabulary. Their server eligibility changes from an empty-history idle session to an owner-authorized idle session with no live run or conflicting pending control. Starting refresh is explicitly destructive: existing broker wrappers are removed before the replacement control begins. Existing HTTP routes retain equivalent behavior.
- **Exported Go APIs / interfaces:** No exported `engine/` type or method signature changes. `session.Session.BeginWorkspaceEnrollment` and `CompleteWorkspaceEnrollment` retain signatures but change their documented/validated lifecycle from pre-prompt-only to idle-without-conflicting-control. The root-internal `WorkspaceEnrollmentAttachment` adds `ResetWorkspaceEnrollment(context.Context) error`: while holding the broker's logical-session serialization, it invalidates the completed catalogue generation, preserves the logical ToolHive session and opaque grant custody, and returns no presentation or credential material. The server adds one broker-only detach/withdraw helper rather than reusing broad session cleanup. No remote broker interface is introduced.
- **Tool schemas:** None — `/tools-connect` and `/tools-cancel` are mecatui client builtins invoking an existing caller-owned control, not model-visible tools. Broker wrappers continue to derive their schemas solely from a verified frozen authenticated catalogue.
- **CLI / config:** No flag, config key, or command argument. `/tools-connect` and `/tools-cancel` retain their bare-command grammar. Broker mode remains Helm-schema constrained to `replicaCount: 1` when `mcp.broker.callbackURL` is configured; no affinity/routing setting is added.
- **Events / persistence:** Reuse the existing opaque `Session.ExternalBinding`, pending workspace-enrollment correlation, and admitted capability names; add no refresh-specific snapshot field. A refresh control on a completed session persists its completed-to-idle reopen together with the pending control transition. Persisted capability names are an upper bound, not proof of executable broker authority: execution additionally requires the exact live binding and installed wrappers. Starting replacement serially withdraws the broker-bearing engine/attachment and invalidates the completed broker catalogue before beginning new enrollment. “Connected” is published only after complete discovery, replacement engine construction, aggregate authority/binding update, and snapshot persistence succeed. For explicit replacement only, compensation also resets a completed broker publication when a later build or persistence step fails, superseding ADR 0322's publication-survival rule; initial pre-prompt enrollment and read-only inventory keep ADR 0322's existing semantics. This is an ordered fail-closed sequence, not a transaction across runtime and storage; fault or restart at any boundary must rehydrate with no executable broker wrapper and require another explicit refresh. No OAuth URL/state/code/token, connector selection, refresh diff, status cache, background worker, or synthetic model/history event is persisted.
- **Security / authority:** Every control call remains session-owner authorized, run-entry/lease serialized, and guarded by the same exact opaque enrollment reference. Retry holds that serialization continuously across cancel-and-begin. ToolHive remains the sole owner of upstream OAuth presentation, callback state, token/grant storage, refresh, and backend injection. Only complete authenticated discovery may install replacement wrappers; cancellation/failure leaves persisted names non-executable and removes the replacement attachment/wrappers rather than retaining stale or partially updated runtime authority. External browser/OAuth work starts only from an explicit control call, never an ordinary prompt. Public projection/logging/model context must not expose private bindings, connector configuration, URLs, callback state, codes, headers, access tokens, or refresh tokens.
- **Compatibility / migration:** Existing clients and wire controls remain source/wire compatible; old clients may continue the original fresh-session enrollment flow. Existing broker-enabled sessions with a still-live matching binding become temporarily broker-tool-unavailable when their owner explicitly starts replacement. Sessions restored after a broker-process restart no longer require `/clear`: an explicit refresh is permitted in the retained conversation. No migration can make a process-random old binding live; it must fail closed until the owner refreshes. This plan intentionally retains the chart's one-replica broker mode and does not promise multi-replica behavior.

## In scope — 3 scenarios, in implementation order

### Scenario 1 — An established idle session can replace its protected-tool bundle

The workspace control currently rejects any non-empty conversation in [`engine/session/workspace_enrollment.go`](../../engine/session/workspace_enrollment.go) and [`internal/adapter/server/workspace_enrollment.go`](../../internal/adapter/server/workspace_enrollment.go). Replace only that temporal restriction: an owned stable session may use the existing opaque whole-bundle control after earlier turns. Starting refresh deliberately removes the active broker wrappers; a connected result installs one complete frozen replacement snapshot for both executable wrappers and durable authority. [ADR 0335](../adr/0335-idle-session-broker-workspace-refresh.md) supplies the authority boundary.

**Acceptance:**
- AC1.1: An owner can begin, observe, retry, and cancel workspace enrollment after at least one completed prompt. The control reopens a completed session to idle while preserving history, then admits the existing gRPC and HTTP control only with no conflicting control; their request/response shapes and aggregate presentation-safe projection remain unchanged.
  - verify: `TestIdleSessionBrokerRefresh_Scenario1_ExistingConversationControls`
- AC1.2: Starting refresh removes the active broker wrappers and invalidates the completed catalogue before the replacement operation begins, while preserving conversation, placement, and unrelated session state. A connected whole-bundle result reports success only after the exact new broker wrappers/names, replacement engine, and durable authority/binding are installed. Fault injection at broker reset, engine build, attachment commit, aggregate completion, and snapshot persistence proves the ordered fail-closed postcondition: no stale or partial broker wrapper is executable and the next explicit refresh can retry. No additive merge, candidate generation, or synthetic model/history notice is introduced.
  - verify: `TestIdleSessionBrokerRefresh_Scenario1_DestructiveCatalogueReplacement`
- AC1.3: A failed, denied, expired, or cancelled replacement leaves broker tools unavailable. It does not restore stale wrappers, retain a partial replacement, or start another replacement transaction automatically.
  - verify: `TestIdleSessionBrokerRefresh_Scenario1_DestructiveCatalogueReplacement`
- AC1.4: A refresh is rejected while an agent run, a pending permission/lazy authorization, or another enrollment refresh is active. A pending refresh rejects every new prompt until it succeeds, fails, expires, or is cancelled; no refresh completion can replace a catalogue mid-run. Retry keeps the session's run-entry/lease serialization continuously from exact cancellation through replacement begin, so a prompt cannot enter between them.
  - verify: `TestInvariant_idle_session_broker_refresh_serialization`

### Scenario 2 — A same-session explicit refresh recovers broker capability after process loss

A broker binding is intentionally process-specific today: [`internal/adapter/server/mcp_broker.go`](../../internal/adapter/server/mcp_broker.go) rejects an old binding after runtime restart. The explicit workspace control becomes the only permitted rebind/recovery path for an established conversation. Ordinary run rehydration treats a missing/mismatched process-local broker binding as broker-unavailable and builds the session engine without broker wrappers; it does not call attach, rebind, discovery, credential refresh, or browser presentation. A later explicit refresh may reuse a ToolHive-held grant only if ToolHive's configured storage and lifecycle permit it. This preserves [ADR 0311](../adr/0311-per-upstream-mcp-broker-oauth-grants.md)'s ToolHive ownership boundary.

**Acceptance:**
- AC2.1: After simulated broker-process loss, a restored owned session remains available for non-broker prompts and exposes no active stale broker wrapper. Ordinary run rehydration builds the engine without broker tools and never attaches, rebinds, discovers, refreshes credentials, or opens browser consent; persisted names remain non-executable without the matching live binding and wrappers.
  - verify: `TestIdleSessionBrokerRefresh_Scenario2_RestartAndExplicitRecovery`
- AC2.2: The owner can invoke the unchanged workspace control in that established session; it creates and commits a fresh attachment/binding, completes the existing ToolHive whole-bundle lifecycle, rebuilds the session engine, and persists the new binding and exact admitted broker names only after verified complete discovery.
  - verify: `TestIdleSessionBrokerRefresh_Scenario2_RestartAndExplicitRecovery`
- AC2.3: Lost, malformed, foreign, or unowned sessions and stale enrollment references remain fail-closed and indistinguishable where ownership concealment requires it. A failed post-restart recovery leaves no partial attachment, catalogue, or replacement binding installed.
  - verify: `TestIdleSessionBrokerRefresh_Scenario2_RestartAndExplicitRecovery`
- AC2.4: A fresh explicit refresh may reuse valid ToolHive-held upstream grants only when the configured ToolHive storage and lifecycle make them available; otherwise ToolHive may require consent. Mecatl's outer attachment, enrollment correlation, and broker credential are never resumed or inferred after process loss, and no upstream connector identity, callback state, endpoint, authorization code, token, or grant reaches controls, snapshots, events, diagnostics, or model-visible content.
  - verify: `TestInvariant_idle_session_broker_refresh_preserves_toolhive_custody`

### Scenario 3 — Mecak8s and mecatui expose truthful ongoing-session refresh behavior

Mecatui currently treats Connect as fresh-session-only in [`cmd/mecatui/ui/mcp.go`](../../cmd/mecatui/ui/mcp.go), while `/tools-connect` dispatches the existing control from [`cmd/mecatui/ui/workspace_enrollment.go`](../../cmd/mecatui/ui/workspace_enrollment.go). Align both surfaces with the server's resolved stable-session eligibility without inventing a connector selector or new response protocol. Update the owning deployment documentation, whose current broker section says Connect is hidden for used/resumed sessions (`user-docs/building/deployment/mecak8s.md`). [ADR 0335](../adr/0335-idle-session-broker-workspace-refresh.md) records the resulting user contract.

**Acceptance:**
- AC3.1: `/tools-connect` and `/mcp` offer the same existing whole-bundle action whenever the owner-authorized broker-capable session is stably idle and the enrollment controller is wired: fresh/not-started, established/connected, terminal-after-failure, and process-lost/unavailable inventory states are eligible. Inventory availability or persisted names never prove connectivity, but they do not suppress this explicit recovery action. Running or awaiting sessions and busy/pending controls are ineligible; pending refresh shows only the existing observe/cancel flow. Bare-command parsing and all generation/session correlation protections remain unchanged.
  - verify: `TestIdleSessionBrokerRefresh_Scenario3_EligibilityAndRecoveryUX`
- AC3.2: Following process loss, mecatui truthfully reports broker tools unavailable until an explicit refresh completes. It does not claim persisted names prove live connectivity, suggest switching to global MCP, or offer a refresh while the session is non-idle.
  - verify: `TestIdleSessionBrokerRefresh_Scenario3_EligibilityAndRecoveryUX`
- AC3.3: User and operator documentation describes refresh after completed turns, prompt blocking while refresh is pending, destructive replacement behavior (broker tools become unavailable on cancellation/failure), explicit same-session post-restart recovery, ToolHive credential custody, and the retained one-replica broker constraint. It does not claim high availability, multi-replica routing, automatic recovery, or guaranteed grant reuse.
  - verify: inspection — `user-docs/building/deployment/mecak8s.md` and `docs/architecture.md` are the owning user/operator references; the existing Helm schema/values single-replica constraint is unchanged. `task docs` and `task site:build` verify documentation integration.

## Out of scope

| Item | Defer-to | Decision |
|---|---|---|
| Remote or durable broker runtime, callback correlation, and distributed attachment ownership | Successor broker architecture | ADR 0335 retains the in-process boundary. |
| Multi-replica session affinity, routing, failover, or takeover | Successor deployment/broker architecture | Broker callback mode remains schema-enforced single replica. |
| Per-connector selection, partial bundle success, or a connector diff/confirmation UI | Future connector-management work | The admitted broker catalogue remains one all-or-nothing configured bundle. |
| Automatic reconnect, OAuth recovery, or browser consent during an ordinary prompt | Future explicitly authorized UX work | Recovery is caller-initiated through `/tools-connect` only. |
| New model prompt instruction, synthetic history message, or refresh event | None | The refreshed tool definitions are sufficient model-facing state. |
| Changing lazy authorization for statically declared tools | ADR 0310 scope | This plan preserves lazy per-tool authorization independently of workspace refresh. |

## Deferred decisions and known risks

- This plan does not claim that a current in-process broker can survive a restart. It specifies a fail-closed, explicit same-session recovery path under the existing single-replica topology.
- The destructive replacement decision avoids candidate-generation complexity. The implementation must nevertheless make the withdrawal of the old attachment/wrappers and the terminal replacement outcome fail closed: no stale or partial broker wrapper may survive a failed refresh.
- ToolHive's provider-specific consent, refresh, retry, and browser presentation behavior remains its contract. Mecatl must not duplicate it to make refresh appear more seamless.
