# Mecatl Studio chat approvals, review, and Escape — acceptance plan

**Contract:** human-reviewed/v2
**Work classification:** Architectural — an exact plan-ask verdict crosses the engine, daemon, public protocol, published SDK, and Studio BFF, replacing session-only authority for this browser path.
**Decision record:** [ADR 0362](../adr/0362-exact-plan-ask-control.md)
**Phase:** Studio design alignment
**Status:** proposed, 2026-09-24. Reconciled with #1847's proposed #1880 interface and validated for Plan / Interface review.
**Delivery:** Split. Review this public control and the Studio interaction contract in an independent Plan / Interface PR before implementation.
**Expected tasks:** deferred to orchestration
**Issue:** [stacklok/mecatl#1848](https://github.com/stacklok/mecatl/issues/1848).
**Plan PR:** added when opened
**Approved baseline:** absent until this Plan / Interface PR merges

Studio shows each actionable permission and plan review beside the transcript event that raised it, with enough arguments or a bounded diff to inspect before deciding. An external MCP authorization handoff has its own panel and lifecycle. Escape consumes one visible layer per key press. The [agent loop](../architecture/agent-loop.md#permission-pause--resume), [original Studio chat contract](studio-chat.md), and [ADR 0351](../adr/0351-mecatl-studio-in-repo-web-ui.md) supply the current engine and browser boundaries.

This plan consumes #1847's proposed [transcript and composer contract](https://github.com/stacklok/mecatl/pull/1880): its `ChatMessage` rows and stable per-render anchors, `run.started | run.event | run.truncated | run.error` stream, exact `{sessionId, runId}` control target, `permission.ask`/`permission.retract`/`approval` deliveries, and `onPreviewTool` callback. #1847 owns the base rows, composer, and responsive layout; this plan owns approval/review cards, their controls, and Escape inside that layout. #1850 owns the reusable side-panel frame; this plan supplies review content and close behavior. The [design review](https://github.com/stacklok/mecatl/issues/1779) checks desktop/mobile interaction evidence. `user-docs/building/deployment/studio.md` is the owning public page for the eventual implementation, not for behavior that is still planned.

## Human decisions

- [x] Focused overlays. — Decision: when a dialog or menu has focus, the first Escape closes only its topmost overlay. A pending ask behind it stays pending. The chat priority order starts on a later press.
- [x] Plan verdict authority. — Decision: add exact run-and-ask preconditions in the daemon and published SDK, classifying this work Architectural. Studio never submits a session-only `resolvePlan` verdict; both live and restored asks use the strict control.
- [x] Continuation. — Decision: approving a plan starts the existing harness proceed continuation after `StopPlanApproved`, whether the ask was live or restored. Iterate is an explicit deny and starts no continuation.
- [x] External authorization. — Decision: opening, rechecking, and cancelling an MCP authorization use its separate session/authorization-ID lifecycle; Escape closes its panel without implicitly cancelling the handoff.
- [x] Draft clearing. — Decision: two distinct Escape presses separated by key release within 500 ms clear a non-empty unsent draft only after every higher layer is absent. The first press only arms and announces the action; repeat events never count.

## Interface contract

- **gRPC / protobuf:** Add unary `HarnessService.ResolvePlanAsk(ResolvePlanAskRequest) returns (ResolvePlanAskResponse)` beside `ResolveRunAsk`. Request fields: `session_id = 1` (non-empty), `expected_run_id = 2` (non-empty), `ask_id = 3` (non-empty), `verdict = 4` (`APPROVAL_VERDICT_DENY`, `ALLOW_ONCE`, or `ALLOW_ALWAYS`; `UNSPECIFIED` invalid). Response fields: `run_id = 1`, `ask_id = 2`, both required echoes. Add `POST /v1/sessions/{id}/controls/resolve-plan-ask` with exact snake-case JSON `{ "expected_run_id": string, "ask_id": string, "verdict": "deny"|"allow_once"|"allow_always" }` and `200 {"run_id": string, "ask_id": string}`; reject unknown keys, trailing JSON, missing IDs, and numeric or unspecified verdicts. The authorized session is resolved before run lookup; an unknown/foreign session stays NotFound, an old/ended/cancelling run is `stale_run_control` (409), and a wrong, ordinary, retracted, or consumed ask is `ask_not_pending` (409). Keep the existing session-only `ApprovePlan` and its HTTP mirror for compatibility; Studio never calls them.
- **Exported Go APIs / interfaces:** Add `agent.(*Run).ResolvePlanAsk(askID string, verdict session.ApprovalVerdict) agent.AskResolution`, atomically consuming only its root plan-originated pending ask; add `agent.AskResolutionNotPlan` for an ordinary-origin mismatch. Keep `Run.Approve` and `ResolveOrdinaryAsk` unchanged. Add `server.(*Service).ResolvePlanAsk(ctx context.Context, id session.SessionID, expectedRunID, askID string, verdict session.ApprovalVerdict) (server.RunAskAcknowledgement, error)`. Add `RunControls.resolvePlanAsk(askId: string, verdict: PlanApprovalVerdict, requestOptions?: RequestOptions)` returning a promise with no value to the public TypeScript SDK; it maps `approve` to allow once, `accept_edits` to allow always, and `iterate` to deny, gates on `ServerFeature.ExactPlanAskControl`, and checks both response echoes. `Session.resolvePlan()` stays source compatible. Run `task api:update`, classify the `engine/CHANGELOG.md` addition, and update SDK API reports in the implementation.
- **Tool schemas:** None — `PresentPlan` already carries full plan text in its `plan` argument and an optional `note`; other tool argument schemas and permission policy inputs do not change.
- **CLI / config:** None — no flag, setting, key binding outside Studio, permission posture, or plan-auto-approval default changes.
- **Events / persistence:** Advertise open feature `exact_plan_ask_control` only where both strict transports work. The new daemon control is acknowledgement-only: live asks resolve on the exact registered run; restored asks revalidate the same run ID, ask ID, and plan origin after lease acquisition, then use a server-owned detached relay. Reserve continuation ownership before consuming an allow. An allow starts one server-owned continuation only after the plan run ends `StopPlanApproved`; deny ends `StopPlanIterate` and starts none. The existing `permission.ask`, `permission.retract`, `approval`, `result`, `authorization.required`, `authorization.resolved`, `steer`, and `steer.outcome` event vocabulary, durable run IDs, and session activity stream remain the evidence source; no new event or persisted field is added. Add Studio `POST /api/v1/sessions/{sessionId}/runs/{runId}/plan-asks/{askId}` with exact `{verdict:"approve"|"accept_edits"|"iterate"}` and a 204 acknowledged response. The BFF calls only the published SDK's exact control; an unsupported feature is 503, stale/consumed targets are 409, and the route never retries a verdict. Add `GET /api/v1/sessions/{sessionId}/authorizations/{authorizationId}/presentation` as an authenticated 302 redirect to the SDK's freshly supplied HTTP(S) URL, with `Cache-Control: no-store`; `POST` `/recheck` and `/cancel` stream the existing Studio run SSE union from the published SDK authorization flow. Regenerate OpenAPI and the browser client from [chat schemas](../../apps/contracts/src/schemas/chat.ts).
- **Security / authority:** Every verdict is bound to an immutable `{sessionId, runId, askId}` tuple captured from one authenticated event, never to the run that happens to be active when a stale card is clicked. The tuple must still match the viewed session and active run; missing correlation makes a card read-only. The daemon, not the tool name or browser state, proves plan origin and lifecycle before mutation. Studio keeps origin/CSRF checks, SDK session-affinity routing, and per-request SDK credentials, does not use a BFF-local pending-ask map for authority, and never falls back to session-only `resolvePlan` or a successor run. A matching request in flight disables its controls; duplicate clicks, ambiguous transport failures, cross-tab repeats, and old cards reconcile from authoritative activity rather than silently sending a replacement verdict. Deny remains dominant over learned allows; allow always cannot override a configured Deny or Ask or grant beyond the existing posture and evaluator. An authorization card uses the exact session/authorization ID through `session.mcpAuthorization(id)`; the BFF redirects its presentation route only to the SDK-validated HTTP(S) URL, with no credential forwarding to that origin. A user-clicked external link uses `target="_blank"` and `rel="noopener noreferrer"`; Studio never embeds, caches, or logs the URL. It is not a permission verdict. Review text and diffs come only from the already scrubbed event projection, are rendered inertly and bounded, and cannot fetch external content. The developer steer trace never includes steer text, content parts, arguments, URLs, headers, or credentials.
- **Compatibility / migration:** The new protobuf, HTTP, Go, and SDK operations are additive under API major 1. Existing `ApprovePlan`, owned-run callbacks, ordinary `RunControls.resolveAsk`, Studio ordinary permission route, session URLs, and #1847 SSE union remain. A Studio deployment enables plan verdict buttons only after a daemon advertises `exact_plan_ask_control` and Studio's lockfile contains an npm-published SDK release with `resolvePlanAsk`; ADR 0351 forbids linking `apps/` to the local SDK. An older server or SDK shows a read-only plan card with an unavailable reason and no session-only fallback. Roll out daemon, publish SDK, then Studio. #1847's proposed transcript plan must be approved and its base rows implemented before this UI implementation; #1848's plan review proceeds independently. #1885 is a separate activity-plan PR and is not a prerequisite.

## In scope — 5 scenarios, in implementation order

### Scenario 1 — inspect and resolve an ordinary tool ask inline

The [existing chat approval reducer](../../apps/web/src/features/chat/chat-state.ts), [approval panel](../../apps/web/src/features/chat/approval-panel.tsx), and [Edit/Write diff parser](../../apps/web/src/features/chat/edit-diff.tsx) provide the starting point. [ADR 0347](../adr/0347-run-id-addressed-prompt-free-controls.md) supplies the exact ordinary-ask control. #1847 supplies the owning transcript row and event/anchor seams.

**Acceptance:**
- AC1.1: a current `permission.ask` appears beside its tool call with tool name, reason, and its event arguments. Edit/Write show a bounded line diff when those arguments parse, with the complete raw arguments still reachable; malformed diffs fall back to escaped raw arguments rather than inventing a change. An absent argument body is labelled unavailable and offers Deny only. Replay does not resurrect an ask after `permission.retract` or `approval`.

- AC1.2: Allow once, Always allow, and Deny each submit the immutable session/run/ask tuple captured with the displayed event to the existing ordinary permission route, only while it matches the active run. A synchronous per-ask in-flight latch and disabled controls allow one local submission; a 409 or lost acknowledgement marks that card uncertain until activity refresh. Neither a stale card nor a repeated click can target a newer ask, and the resolved verdict is shown only after an acknowledgement or matching activity.

### Scenario 2 — review and decide a plan on the exact ask

`PresentPlan` carries its full text in the `plan` argument of [the signalling tool](../../engine/agent/presentplan.go); the [plan gate](../architecture/agent-loop.md#plan-approval-gate) keeps allow, accept edits, and deny distinct. [ADR 0362](../adr/0362-exact-plan-ask-control.md) owns the new strict route.

**Acceptance:**
- AC2.1: a `PresentPlan` ask shows the presented `plan` text and optional note, linked to the assistant's plan turn, with Approve & run, Auto-accept edits, and Iterate controls. Raw arguments remain inspectable. Missing or malformed plan text disables both approving controls but leaves Iterate available. Client tool-name classification only chooses presentation; the daemon checks plan origin. Iterate is an explicit deny, keeps the session in plan mode, and never starts execution.
  - verify: vitest:apps/web/src/features/chat/plan-review.test.tsx#cmVuZGVycyB0aGUgcHJlc2VudGVkIHBsYW4gYW5kIHRocmVlIGRpc3RpbmN0IHZlcmRpY3Rz — `plan-review.test.tsx :: "renders the presented plan and three distinct verdicts"`.
- AC2.2: a live or restored plan ask accepts at most one verdict for the exact run and ask. The daemon refuses old run IDs, different/ordinary asks, competing verdicts, and replayed submissions before any mode flip or continuation. On allow, it records `StopPlanApproved`, flips mode at the terminal boundary, and starts exactly one fresh proceed run; on deny it records `StopPlanIterate` and no proceed run. A lost unary response cannot cancel an accepted run.
  - verify: `TestADR_0362_LiveAndRestoredExactPlanAsk` and `TestStudioPlanAsk_Scenario2_DuplicateAndStaleVerdicts` — service-level live, restart, lease-race, and competing-control proofs.
- AC2.3: Studio's plan route passes only the three product verdict strings to the published SDK method, validates exact run/ask acknowledgement, and exposes 409 on stale or duplicate targets. After an allow acknowledgement, the browser follows durable activity across the old run's terminal event and waits for the new run ID before claiming execution started; if the first activity stream closes before that run appears, it reconnects from its last cursor with bounded polling and reports uncertainty at the bound. Without the advertised feature or released SDK, the review is read-only with an explicit unavailable reason; the BFF never invokes `Session.resolvePlan()`.

### Scenario 3 — external authorization stays a separate lifecycle

The [SDK authorization handle](../../sdk/typescript/src/mcp-authorization.ts) uses session plus authorization ID, while [authorization events](../../sdk/typescript/src/events.ts) carry safe correlation and status. [ADR 0348](../adr/0348-typescript-sdk-mcp-authorization-lifecycle.md) keeps this lifecycle separate from a permission verdict.

**Acceptance:**
- AC3.1: `authorization.required` shows display name, status, and an explicit Open authorization action in a review panel attached to its run/call; `authorization.resolved` retires the action and shows the observed outcome. A user-clicked new-tab link visits the authenticated BFF presentation route, which retrieves and redirects to a fresh HTTP(S) URL without embedding or retaining it. Pending, expired, cancelled, and failed states are labelled without implying that opening the page granted access.

- AC3.2: Recheck and Cancel operate on the exact session/authorization ID through the SDK flow, expose its pending/settled/continuation events through the existing SSE union, and refuse duplicate local submissions while one flow is active. A later ordinary permission ask from that continuation uses its own exact run/ask verdict route. Closing the panel with Escape leaves the authorization unchanged.

### Scenario 4 — Escape consumes one chat layer per press

The existing [shortcut provider](../../apps/web/src/features/shortcuts/shortcut-provider.tsx) and [chat composer](../../apps/web/src/features/chat/chat-composer.tsx) own browser key events under [ADR 0351](../adr/0351-mecatl-studio-in-repo-web-ui.md); #1850 supplies the shared side-panel frame. Escape works with pointer or keyboard focus and does not replace native button activation.

**Acceptance:**
- AC4.1: when a dialog or menu is open with focus inside it, the first Escape closes only the topmost overlay and restores its trigger focus. Its event cannot bubble into chat and neither denies a hidden ask nor cancels a run. A second press is evaluated against the then-current chat state. An overlay that momentarily loses focus while open still suppresses the chat handler until it closes.
  - verify: vitest:apps/web/src/features/chat/chat-escape.test.tsx#Y2xvc2VzIHRoZSBmb2N1c2VkIG92ZXJsYXkgYmVmb3JlIHRvdWNoaW5nIGEgcGVuZGluZyBhc2s — `chat-escape.test.tsx :: "closes the focused overlay before touching a pending ask"`.
- AC4.2: with no overlay, each non-repeated Escape performs exactly the first applicable action: collapse the active non-empty text selection; explicitly Deny the current ordinary ask or Iterate/deny the current plan ask; close the review/authorization or other side panel; cancel the exact live run; then consider draft clearing. A pending ask takes precedence over panel and run, including after reattachment. An authorization handoff is not treated as a permission ask and its panel only closes. A failed/ambiguous verdict remains visible for reconciliation and does not fall through to cancel. If an exact plan verdict is unavailable on the connected server, Escape reports that inability and sends no substitute verdict or run cancellation.
  - verify: vitest:apps/web/src/features/chat/chat-escape.test.tsx#dGFrZXMgZXhhY3RseSBvbmUgRXNjYXBlIGFjdGlvbiBwZXIga2V5IHByZXNz — `chat-escape.test.tsx :: "takes exactly one Escape action per key press"`.
- AC4.3: with no higher layer and a non-empty unsent draft, the first Escape only arms a visible/screen-reader clear hint. Only a released second non-repeat press within 500 ms clears it; expiry, editing, navigation, overlay opening, focus change, composition, or a new higher layer disarms it. An Escape that closed an overlay, denied an ask, closed a panel, or cancelled a run cannot arm the draft. An empty draft causes no action.
  - verify: vitest:apps/web/src/features/chat/chat-escape.test.tsx#cmVxdWlyZXMgYSByZWxlYXNlZCBzZWNvbmQgRXNjYXBlIHRvIGNsZWFyIGFuIHVuc2VudCBkcmFmdA — `chat-escape.test.tsx :: "requires a released second Escape to clear an unsent draft"`.

**Acceptance:**
- AC5.1: the active card hints at its actual Escape action (`Deny`, `Iterate`, or `Close`) only when that action is available; a live run hints `Stop`, and a draft hints the guarded double press only when eligible. Native Enter/Space activate a focused verdict button without also sending the composer. The shortcuts reference describes the layered Escape behavior, visible focus returns after panel/overlay close, and labels, status, and diff additions/removals work at 320/500/desktop widths without color alone.

## Deferred decisions and known risks

- No material interface or behavior decision is deferred. A daemon failure after it acknowledges an approved plan but before a continuation starts may leave a temporarily uncertain outcome; Studio reconciles activity and never reports successful execution without a continuation result.
